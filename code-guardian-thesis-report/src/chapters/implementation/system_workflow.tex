\section{System Workflow}
\label{sec:impl-pipeline}

This section explains how Code Guardian turns JavaScript/TypeScript code into vulnerability findings and repair suggestions, implementing the design from Chapter~\ref{chap:concept} against the requirements in Chapter~\ref{chap:analysis} (R3, R4, R5).

\subsection*{End-to-End Flow}

Two execution paths matter in the prototype: a \emph{structured diagnostics} path that emits JSON findings for editor diagnostics, and an \emph{interactive analysis} path that emits Markdown explanations in a WebView with follow-up Q\&A. A run is triggered automatically while editing (debounced) or explicitly via a command (analyse selection, analyse file, scan workspace), and the chosen scope determines how much context is included. The extension extracts the relevant code fragment and its location: for real-time diagnostics, the default is the enclosing function found by depth-first AST traversal via the TypeScript language service, with a 2\,000-character size guard; for selection analysis, the unit is the selected region; for file analysis, the entire document. If RAG is enabled and initialised, the system retrieves security-knowledge snippets through a local embedding model and HNSW index and appends the guidance to the prompt; the real-time diagnostics path is kept lightweight to preserve responsiveness, while RAG is primarily used in interactive WebView and batch-scan workflows. The local Ollama model is invoked with output constraints matching the workflow: structured diagnostics request a JSON array of issues with defensive parsing (strip Markdown fences, extract the first JSON array substring, validate fields) and degrade safely to empty findings on parse failure; interactive analysis streams Markdown to the WebView. Findings render as VS Code diagnostics (squiggles, Problems panel, hover tooltips) with optional Quick Fix actions; results are cached by (snippet, model, mode) under LRU + TTL so repeated edits do not re-invoke the model.

Although inference is probabilistic, the orchestration is deterministic: for a fixed input snapshot, active model, and prompt mode, scope extraction, prompt-assembly structure, parsing, localisation mapping, and diagnostic emission follow a fixed sequence with explicit guards. This isolates model effects during debugging and evaluation. On each trigger the extension extracts and validates scope, computes a content-based cache key, returns immediately on hit, and on miss assembles the prompt (optionally with RAG), calls the model, validates the JSON response, maps snippet-relative line numbers to document positions, caches the result, and renders.

\subsection*{Debouncing and Workflow Modes}

A debouncer suppresses analysis on every keystroke: each document-change event resets a timer, and analysis runs only after an 800\,ms pause. The real-time workflow uses function-level scope plus the 2\,000-character guard ($\sim$400--500 tokens) to keep inline feedback within acceptable bounds on consumer hardware. On-demand selection or file analysis applies a 20\,000-character file guard ($\sim$4\,000--5\,000 tokens) so prompts fit the effective context window of smaller local models (8K--16K) with headroom for RAG context and response generation. The workspace scanner iterates JS/TS files (excluding \texttt{node\_modules}) and aggregates findings into a dashboard; files above 500\,KB are skipped so memory use stays bounded across large monorepos.

\subsection*{Pipeline Gates}

Four configurable gates sit between the consensus filter and diagnostic emission, each toggleable through extension settings. \emph{Confidence assignment} stamps every stage-1 finding with a confidence score and a \texttt{detectionSource} provenance tag --- both-pass agreement is $1.0$, and the single-pass fallback (which would otherwise drop findings silently) keeps them at $0.3$ so they remain visible to downstream gates. The opt-in \emph{confidence gate} applies a threshold in $[0,1]$ before stage~2 (default $0$, no gating); at $\geq 0.67$ on three passes only findings agreed by at least two survive. The opt-in \emph{hybrid SAST fusion} runs Semgrep once over the snippet, and any LLM finding overlapping a Semgrep finding on line range plus canonical category is promoted to \texttt{detectionSource: 'hybrid'} with confidence~$1.0$; LLM-only findings keep their inter-run confidence. \emph{Repair syntax validation} parses every \texttt{suggestedFix} after stage~2 and tags findings with an \texttt{autoApplicable} boolean (and a short rejection reason such as \texttt{prose\_not\_code}); the IDE quick-fix surface uses this to decide whether to offer one-click apply or a preview-first action.

\subsection*{System Prompt and Latency Telemetry}

The stage-1 system prompt is a tight ${\sim}80$-token instruction; JSON-mode decoding plus the response schema enforce output shape, so a verbose response-format example block is unnecessary. Per-call latency is reported as \texttt{inferenceTimeMs} plus \texttt{parseTimeMs} so any latency change can be attributed unambiguously. Inference dominates the total by more than $99\%$ in measured micro-evaluation; the prompt size is therefore the dominant prefill-token cost lever.

\subsection{Audit Mode: AST + LLM Hybrid Pipeline for Whole-Project Scans}
\label{sec:impl-audit-mode}

Inline real-time analysis uses function-level scope to stay inside the 1.5\,s latency budget; whole-project audits run under a different scope, with no per-keystroke deadline, so the system can afford a deeper structural analysis. Audit mode is the deployment of the workspace dashboard command (\texttt{codeSecurity.workspaceDashboard}). It is enabled by default through the new setting \texttt{codeGuardian.enableAuditMode}; setting it to \texttt{false} reverts the dashboard to the legacy LLM-only function-scoped behaviour.

The pipeline runs in two stages, deterministic before semantic.

\paragraph{Stage 0 --- AST project map.}
\texttt{src/projectMapBuilder.ts} walks the workspace using Node \texttt{fs} (skipping \texttt{node\_modules}, \texttt{cypress}, \texttt{tests}, etc.) and parses every \texttt{.js}/\texttt{.ts}/\texttt{.jsx}/\texttt{.tsx} file with the TypeScript compiler API. For each file the visitor records: imports (\texttt{require()} and \texttt{import} declarations), top-level exports, request-input usage (\texttt{req.body}, \texttt{req.query}, \texttt{req.params}), and a curated set of direct sink shapes that map cleanly to the canonical taxonomy:

\begin{itemize}
  \item \texttt{eval(\dots)}, \texttt{Function(\dots)} --- CWE-95 code injection, with the request-input chain reported when the first argument is \texttt{req.body.X};
  \item \texttt{child\_process.exec / execSync / spawn} --- CWE-78 command injection;
  \item \texttt{crypto.createHash('md5'|'sha1'|'rmd160')} --- CWE-327 weak crypto;
  \item \texttt{require(<dynamic>)} --- CWE-22 dynamic-path require;
  \item ObjectLiteralExpression with key \texttt{\$where} and a TemplateExpression value --- CWE-943 NoSQL injection via \texttt{\$where} interpolation;
  \item RegularExpressionLiteral matching the nested-quantifier shape \texttt{(X+)+ / (X*)+ / (X+)*} --- CWE-1333 ReDoS;
  \item ObjectBindingPattern with $\geq 3$ fields whose initialiser is \texttt{req.body}, \texttt{req.query}, or \texttt{req.params} --- CWE-915 mass assignment.
\end{itemize}

Each detection is a \texttt{SecurityIssue} object tagged \texttt{detectionSource:\,'ast'} with confidence~$1.0$. The whole project map is built in well under a second on the M4 Max profile; the cost is bounded by file count and is independent of model latency.

\paragraph{Stage 1 --- per-file LLM analysis.}
After the AST map is built, the workspace scanner iterates the same file list and analyses each file with the existing \texttt{analyzeCodeWithLLM} pipeline (RAG-augmented when enabled). The whole-file scope requires a larger context window than the inline mode's 2\,000-character chunks; the implementation requests \texttt{num\_ctx:\,16384} so a 100--150-line source file plus the system prompt and RAG snippets fit with headroom for output. LLM findings are tagged \texttt{detectionSource:\,'llm'}.

\paragraph{Stage 2 --- union and corroboration.}
For each file, AST detections (Stage 0) and LLM findings (Stage 1) are unioned by \texttt{workspaceScanner.mergeIssues}. Findings on the same line collapse into a single entry tagged \texttt{detectionSource:\,'hybrid'}, signalling that both detectors agreed. The dashboard renders the three sources distinguishably so the developer can read the detection provenance directly from the diagnostic.

\paragraph{Why the AST is independent of the LLM.}
An earlier audit-mode iteration prepended the AST findings to the LLM's system prompt as ``known-risky sinks'' context. The model interpreted this as ``these are already flagged, do not re-flag'' and emitted near-zero findings. The current pipeline therefore runs the two detectors in parallel with no shared prompt context, leaving the LLM unaware of the AST findings; the union step does not require the LLM to confirm AST detections. This separation also means the deterministic rate (Section~\ref{sec:eval-reproducibility-metric}) of audit mode equals the LLM rate, since AST findings are byte-identical across runs by construction.

\paragraph{Performance.}
The 6-file targeted run on OWASP NodeGoat (Section~\ref{sec:eval-r1-realworld}) executes in 117\,s under audit mode versus 884.5\,s for the inline-scoped 26-file run. The AST stage adds approximately 30\,ms per 100 files; per-file LLM cost is dominated by the larger \texttt{num\_ctx} (16K tokens) which raises per-call latency from a function-chunked stage-1 baseline of 2\,216\,ms median to 19\,s median for whole-file scope. The latency increase is acceptable because audit mode is invoked explicitly, not on every keystroke. Files above 500\,KB are skipped to keep memory bounded across large monorepos.
