The evaluation in Chapter~\ref{chap:evaluation} closes a privacy-preserving slice of the IDE-security space, but it also exposes specific gaps that further work should address. The directions below are grouped into three categories: \emph{engineering} (improvements that strengthen the delivered system on its current scope), \emph{methodology} (changes to how the system should be measured), and \emph{open research questions} (effects whose causes are not yet understood).

\subsection{Engineering Directions}
\label{sec:fw-engineering}

\paragraph{False-positive control beyond inter-run agreement.}
The pipeline already includes a per-finding confidence score from inter-run agreement, a configurable confidence gate, and an opt-in hybrid SAST-fusion step that promotes LLM findings corroborated by Semgrep (Section~\ref{subsec:confidence-abstention}). The remaining work is to extend the gate beyond agreement: explicit abstention prompting (asking the model to declare uncertainty), calibrated confidence rather than the current agreement-as-confidence proxy \cite{kadavath2022know,spiess2024calibration}, and a confidence-aware ranking surface in the IDE so high-confidence findings are visually distinct from low-confidence ones. The aggregate-FPR result (only \texttt{qwen3:8b+RAG} and \texttt{gemma3:1b+RAG} keep FPR below 100\,\%) suggests that any future deployment that broadens the model pool will need a calibration layer that is not coupled to multi-pass agreement, since smaller models can be self-consistently wrong.

\paragraph{Stronger context modelling across files.}
Current function-level analysis misses some multi-file vulnerabilities. A regex-based import / sink resolver surfaces validator-package presence and category-tagged sinks (Section~\ref{sec:impl-tech-stack}); its empirical lift on the four zero-recall categories proved marginal. The natural next step is to replace the regex resolver with lightweight static analysis (taint-style source-to-sink traces using a TypeScript-aware parser), which would provide structurally grounded cross-function context rather than lexical hints. Code-property-graph approaches \cite{yamaguchi2014cpg} and lifecycle-aware taint analyses \cite{arzt2014flowdroid} are established reference points for this work; an embedded JS/TS analogue could be exposed to the LLM as additional context fields rather than as competing detections, preserving the deterministic-before-semantic ordering that already structures the audit-mode pipeline.

\paragraph{Safer repair generation beyond syntax validation.}
The pipeline includes a syntax check (\texttt{@babel/parser}) on every \texttt{suggestedFix} and reports the auto-applicable rate alongside the manual review (Section~\ref{sec:eval-r3-auto-applicable}). Remaining work is to layer a TypeScript type-check pass on top of the syntax check, run the local test suite (when present) on the patched buffer before offering a one-click apply, and re-run the analyzer on the patched code to verify the original finding is gone and no new finding was introduced. Modern neural-repair work \cite{xia2022alpharepair,zhu2021recoder} provides architectural references for treating the patch as a structured edit rather than a free-form string, which would tighten the residual 9.68\,\% structural-emit failure mode (mid-statement truncation, unterminated regex literals).

\paragraph{Robustness against adversarial inputs.}
The current adversarial harness (\texttt{evaluation/privacy/prompt-injection-test.js}) covers 12 cases at 100\,\% leak-free and 100\,\% detection-survival rates (Section~\ref{sec:eval-r5-prompt-injection}). Future work should extend the corpus to several hundred cases, add retrieval-poisoning attacks against the signed corpus (e.g.\ tampered files staged at known cache paths), and measure performance under multi-turn injection through the contextual Q\&A WebView. Retrieved knowledge should additionally include richer provenance and stronger filtering, and prompts should consistently treat project code as untrusted input data.

\subsection{Methodological Directions}
\label{sec:fw-methodology}

\paragraph{Broader evaluation corpora.}
The current 101-case dataset is useful for controlled iteration but too small for broad claims. Future evaluation should run against larger and externally-authored JavaScript-applicable corpora --- in particular DiverseVul, Big-Vul, and PrimeVul \cite{chen2023diversevul,fan2020bigvul} as filtered to JS/TS samples, and the security-specific suites CyberSecEval and LLMSecEval \cite{bhatt2023cyberseceval,tony2023llmseceval}. Coverage on real-world vulnerable repositories such as DVNA, NodeGoat, and Juice Shop should be expanded beyond the present single-project NodeGoat slice. JavaScript ports of the OWASP Benchmark and NIST Juliet suites \cite{owaspBenchmark,nistJuliet}, when available, should also be incorporated, since both currently target Java and C/C++ only.

\paragraph{Inter-rater reliability for repair quality.}
The 25-sample R3 manual review was performed by a single reviewer; no inter-rater reliability was measured (Section~\ref{sec:eval-r3}). A two-rater protocol with Cohen's $\kappa$ on at least a 10-case overlap, scaled to the full 25-case set if resources allow, would substantially strengthen the 68\,\% combined-correct claim. The deterministic auto-applicable rate complements this on the full $n=279$ sample, but does not substitute for inter-rater agreement on the qualitative dimensions (semantic correctness, strategy alignment, executable-code share).

\paragraph{Pre-registered configuration selection.}
The headline configuration (\texttt{qwen3:8b+RAG}, three runs, gate $\geq 0.67$) was identified by post-hoc evaluation across ten model$\times$mode configurations rather than declared before the sweep (Section~\ref{sec:eval-summary}). The held-out 71/30 split addresses threshold tuning but not configuration selection. A future evaluation cycle should pre-register the selection protocol on a separate development corpus before the test corpus is touched, and report the protocol document alongside the evaluation harness.

\paragraph{Workflow impact and developer studies.}
R4 is currently measured by latency only. Workflow impact should be validated with developer studies measuring usability (SUS), cognitive load (NASA-TLX), and time-to-fix metrics \cite{brooke1996sus,hart1988nasa}, ideally as a small-$n$ controlled walkthrough (3--5 participants, 2-hour sessions) at first and a larger study once the deployment profile is stable. Independent user studies of AI-assisted secure coding \cite{perry2023users,sandoval2023lost} provide methodological templates that translate directly to the Code Guardian deployment profile.

\subsection{Open Research Questions}
\label{sec:fw-research}

\paragraph{Why does only \texttt{qwen3:8b} achieve acceptable FPR?}
Of the ten model$\times$mode configurations evaluated, only \texttt{qwen3:8b+RAG} and \texttt{gemma3:1b+RAG} hold sample-level FPR below 100\,\%; the rest flag every secure sample at least once even with the inter-run gate. This is the most striking unexplained result in the evaluation. Three hypotheses are worth probing: (i) a \emph{parameter-count threshold} effect, where 8B is the smallest scale at which contextual reasoning about \emph{absent} sinks becomes possible; (ii) an \emph{instruction-tuning} artifact, where the \texttt{qwen3} chat post-training specifically discourages over-flagging while code-specialized models like \texttt{codellama} are tuned toward code completion rather than abstention; and (iii) an interaction with the \emph{structured-output contract} itself, where models with weaker JSON adherence inflate FPR by emitting findings to satisfy the schema. These hypotheses are testable: ablations across additional 7B, 8B, and 13B models, with and without instruction tuning, on the same prompt would distinguish (i) from (ii); replacing JSON-mode with free-form output and re-parsing would disambiguate (iii).

\paragraph{The structural recall ceiling.}
Three canonical categories register zero recall under the headline configuration --- improper-auth, input-validation, and weak-encryption (Section~\ref{sec:eval-error-analysis}). The qualitative analysis identifies the input-validation gap as a genuine reasoning failure on real-world library code where the validation gap is implicit in dense utility logic. Closing this gap requires reasoning about \emph{absent code}, which is in turn linked to whether a lightweight TypeScript-aware taint graph (Section~\ref{sec:fw-engineering}) can recover the missing context without full interprocedural analysis. The research question is whether a graph-grounded RAG context (chunks retrieved against a code-property-graph index rather than a flat knowledge corpus) lifts recall on absent-validation cases without inflating FPR --- a hypothesis no reviewed system has yet tested in the local-deployment envelope.

\paragraph{Trust calibration in IDE security feedback.}
The deployment-profile recommendations in the conclusion (Table~\ref{tab:conclusion-deployment-profiles}) are framed as \emph{indicated by measurement}, not as universally validated defaults. Whether the measured accuracy levels translate to practical adoption depends on developer trust, alert fatigue, and the way confidence signals are surfaced in the editor \cite{johnson2013don,christakis2016developers}. Open questions include: at what FPR does developer trust collapse irreversibly even after model improvements? Does visible inter-run confidence change accept rates on borderline findings? Do AI-assisted secure-coding effects observed in cloud studies \cite{perry2023users} reverse, attenuate, or persist when the assistant runs locally with structured output and developer-controlled remediation? Answering these questions requires longitudinal field deployments rather than benchmark runs.

\paragraph{Generalization beyond JavaScript/TypeScript.}
The two-stage pipeline, AST + LLM hybrid, signed-corpus mechanism, and evaluation harness are language-agnostic in design but were instantiated only for JS/TS in this thesis. The open question is whether the headline metrics transfer to Python, Java, and Go under matched local-model configurations, or whether they reflect properties of the JS/TS sink ecosystem (lexically-explicit \texttt{eval}, \texttt{exec}, \texttt{innerHTML}, prototype pollution patterns) that other language ecosystems do not share. A controlled multi-language replication on the equivalent canonical-taxonomy slice would put a number on this generalization claim.
