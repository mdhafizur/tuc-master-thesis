This chapter consolidates the headline outcomes, names the residual limitations and threats to validity, and states the deployment implications. The detailed per-requirement evidence is reported in Chapter~\ref{chap:evaluation}; the cross-cutting interpretation is developed in Section~\ref{sec:eval-comparative}.

\section{Summary of Contributions}

The thesis delivers \textbf{Code Guardian}, a privacy-preserving secure-coding assistant for JavaScript and TypeScript that runs as a VS Code extension with all inference on-device through a local Ollama instance. A synchronous egress gate blocks every non-loopback connection by default, and the optional retrieval store reads from a signed local corpus of CWE, OWASP, and CVE guidance, so no source code or analysis artifact leaves the developer's machine. The detection layer is structured as a \textbf{two-stage detect-then-repair pipeline}: Stage~1 emits structured JSON findings under JSON-mode decoding with a fixed schema, and Stage~2 generates one $\{\,\texttt{code}, \texttt{language}\,\}$ repair per finding under developer-controlled apply or preview. Stability is reinforced by a \textbf{multi-pass consensus filter and confidence gate} that score each finding by inter-pass agreement across seeded runs and suppress unmatched findings before Stage~2 invocation when the gate is enabled.

For whole-project scans the system layers a \textbf{hybrid AST+LLM audit pipeline} on top of the detection stage: a deterministic AST sink scanner runs in parallel with the LLM and unions findings, lifting recall on OWASP NodeGoat from $3/7$ inline to $6/7$ in audit mode, with three entries caught by the AST scanner alone, two by the LLM alone, and one corroborated by both, so each detector surfaces findings the other does not see (Section~\ref{sec:eval-r1-realworld}); because NodeGoat is a single project ($n=7$ documented entries) plausibly present in the model's pre-training data, this result is treated as a case study rather than a population estimate. The contribution is anchored by a \textbf{reproducible evaluation harness} that ships with the 101-case curated corpus, a 15-case external corpus drawn from NodeGoat, Juice Shop, and three named CVEs, three SAST baselines (Semgrep, CodeQL, ESLint), and a deterministic per-repair syntax validator that scales R3 evidence beyond manual review. The whole system follows a \textbf{requirements-driven design} where R1 accuracy, R2 consistency, R3 repair quality, R4 usability, and R5 privacy shape the pipeline, prompt contracts, harness, and deployment profiles end-to-end, with the per-requirement evidence consolidated in the cross-requirement synthesis (Section~\ref{sec:eval-cross-requirement}).

\section{Key Findings}
\label{sec:conclusion-key-findings}

The headline finding is that \textbf{local vulnerability detection is feasible inside the IDE}. On the held-out 30-case TEST split (Section~\ref{sec:eval-r1-heldout}), the \texttt{qwen3:8b+RAG} configuration with the inter-run confidence gate selected on TRAIN reaches F1 61.11\,\% at FPR 0\,\%, which is the externally-valid figure carried into deployment-profile reasoning; on the curated 101-case full corpus the same configuration reaches F1 74.07\,\% with precision 78.13\,\% (Section~\ref{sec:eval-r1}), and the 17.7-point TRAIN--TEST gap is consistent with curated-corpus optimism and bounds how far the in-sample headline generalizes. The function-level scope works well when the dangerous API is lexically present, less well when reachability depends on frame conditions outside the scope. Retrieval augmentation, in turn, is \textbf{per-model rather than universal}: it lifts the strongest 8B-parameter model and degrades smaller and code-specialized ones, and only the \texttt{codellama} degradation survives Bonferroni correction across the five paired McNemar tests, a result consistent with RESCUE's report that conventional RAG does not significantly improve secure code generation \cite{shi2025rescue}.

On the operational side, the measurements show that \textbf{quality-oriented modes belong on demand, not always-on}: function-level scoping, debouncing, and caching make local analysis usable in selected workflows, but the highest-quality configuration's stage~1 median exceeds the strict interactive-inline threshold, and inference accounts for more than 99\,\% of the response time, so further latency improvements require model or architectural changes (Section~\ref{sec:eval-r4}). The \textbf{repair contract scales to the full evaluation set}: the structural \texttt{\{code, language\}} contract reaches a 90.32\,\% auto-applicable rate on the full $n=279$ stage-2 output (Section~\ref{sec:eval-r3}), where auto-applicability measures only whether the IDE quick-fix surface can insert the suggestion without further editing. Semantic correctness is a strictly stronger bar and is reported separately as 17 / 25 ($\approx 68\,\%$, 95\,\% Wilson CI $[48\,\%, 83\,\%]$, single rater) under a 25-sample manual review; the residual auto-applicable rejections are model-side structural defects (mid-statement truncation, unterminated regex literals) rather than prose paraphrases of the fix.

\section{Limitations}
\label{sec:conclusion-limitations}

On \textbf{scope and statistical power}, the system handles common vulnerability patterns but remains limited for deep cross-file reasoning without full static data-flow analysis: three semantic categories register zero recall under the canonical taxonomy, and a regex-based import / sink resolver provides lightweight cross-snippet hints without surfacing new instances in those categories. The 101-case corpus aligns with contemporary curated benchmarks (CWEval at 119 tasks, IRIS at 120 vulnerabilities) but does not generalize to production repository scale, and the small sample size limits statistical power: only the \texttt{codellama+RAG} degradation survives Bonferroni correction, and the 95\,\% exact-binomial CI for the headline 10\,\% FPR is $[2.1\,\%, 26.5\,\%]$ on $n=30$ secure cases. The 15-case external corpus and the standalone NodeGoat real-world run both draw from public sources (NodeGoat, Juice Shop, three named CVEs) almost certainly present in pre-training data, so the headline numbers on these cases (external corpus F1 63.64\,\%; NodeGoat audit-mode 6/7) may reflect partial memorization and are read as case studies rather than population estimates.

The evaluation also has \textbf{no head-to-head comparison against cloud LLMs or commercial SAST}: it compares against three open-source SAST baselines (Semgrep, CodeQL, ESLint) but not against cloud LLMs (GPT-4, Claude) or commercial SAST suites (Snyk Code, SonarQube), because running cloud LLMs on the corpus would violate the system's own threat model (R5 forbids code exfiltration) and commercial SAST products require source upload or proprietary licensing. Both the curated 101-case corpus and the 26-class canonical taxonomy were authored by the candidate, raising \textbf{curator bias and construct-validity} concerns; three mitigations are in place: every case is sourced from an authoritative public corpus and aligned with CWE IDs where applicable, the held-out 71/30 split (Section~\ref{sec:eval-r1-heldout}) keeps threshold tuning off the TEST cases, and the taxonomy is pinned by a snapshot test with per-canonical-category counts emitted in every run JSON so an external reviewer can re-bucket the raw findings under a different taxonomy and re-score.

On \textbf{repair correctness, hardware profile, and configuration selection}, repairs are model-generated and may change behavior, so although the pipeline includes a syntactic auto-applicability check that scales to the full evaluation set, this is a strictly weaker signal than functional verification (a parse-clean fix can still be semantically wrong) and the 25-sample manual review was performed by a single reviewer with no inter-rater reliability measured. All latency measurements come from a single Apple~M4~Max profile (16 cores, 64\,GB~RAM) with deterministic decoding (\texttt{temperature=0}, fixed seed), so reported values are descriptive measurements under a documented environment rather than hardware-independent constants; developer satisfaction, trust, and adoption were not evaluated under a controlled walkthrough, leaving R4 evidence latency-only. The headline configuration (\texttt{qwen3:8b+RAG}, three runs, gate $\geq 0.67$) was identified by post-hoc evaluation across ten model$\times$mode configurations rather than declared before the sweep; the held-out 71/30 split addresses threshold tuning on the same cases as the headline but does not address selection of the model and retrieval mode themselves, and per-configuration metrics are reported alongside the headline (Section~\ref{sec:eval-r1}) so the selection is auditable. Finally, the approved task specified evaluation on \textbf{Juliet and OWASP Benchmark}, but neither targets JavaScript --- Juliet is published by NIST in C/C++ and Java only, and the OWASP Benchmark Project is a Java application --- so the delivered evaluation substitutes two CWE-mapped JavaScript corpora (the 101-case primary corpus, 71 vulnerable + 30 secure, and the 15-case external corpus) that preserve the property the named benchmarks provide (CWE-mapped, vulnerability-tagged samples drawn from authoritative sources) in the target language; under the headline configuration the external corpus reaches F1 63.64\,\% versus the curated 74.07\,\%, an approximately 10-point gap concentrated in framework-level weakness classes that the function-level scope does not see. The substitution was discussed with the supervisor during the implementation phase.

\section{Conclusion}

Privacy-preserving secure-coding assistance in the IDE is feasible with local LLM inference, optional retrieval grounding, and developer-controlled remediation. Local LLM modes achieve much higher vulnerable-case recall than SAST baselines, while deterministic tools retain better false-positive control and lower latency; retrieval augmentation improves some models and degrades others. The measurements indicate that practical local vulnerability assistance without code exfiltration is achievable under the evaluated configurations; production use still requires explicit policy choices for model profile, acceptable FPR, and when to prefer lightweight inline feedback over audit-oriented analysis.
