\chapter{Detailed Case Studies}
\label{appendix:case-studies}

This appendix walks five representative outcomes from the evaluation --- true positive with effective repair, false positive on secure code, false negative on a context-dependent pattern, partial repair, and a multi-CWE finding --- and shows how the measured aggregate metrics translate into per-case IDE behaviour.

\section{Case 1: True Positive with Effective Repair}
\label{sec:case-tp-good}
SQL injection in an Express route detected by \texttt{qwen3:8b+RAG}.
\begin{lstlisting}[caption={SQL injection vulnerability (CWE-89) and the model's repair}]
// Vulnerable
app.get('/user/:id', (req, res) => {
  const userId = req.params.id;
  const query = `SELECT * FROM users WHERE id = ${userId}`;
  db.query(query, (err, results) => res.json(results[0]));
});
// Model output: {"cwe":"CWE-89","lineStart":3,"lineEnd":3,
//   "fixedCode":"const query = 'SELECT * FROM users WHERE id = ?';\ndb.query(query, [userId], ...)"}
\end{lstlisting}
Clean true positive with correct location and CWE, minimal parameterised repair, intent preserved. Low-friction remediation that developers can apply immediately.

\section{Case 2: False Positive (Over-Sensitivity)}
\label{sec:case-fp}
Secure username sanitisation flagged by \texttt{gemma3:4b} (LLM-only).
\begin{lstlisting}[caption={Secure input validation flagged as CWE-94}]
function sanitizeUsername(username) {
  const sanitized = username.replace(/[^a-zA-Z0-9_]/g, '');
  if (sanitized.length < 3 || sanitized.length > 20) throw new Error('...');
  return sanitized;
}
// Model output: {"cwe":"CWE-94","message":"Potential code injection in replace()"}
\end{lstlisting}
The whitelist regex and length checks are appropriate; the CWE label is mismatched. Illustrates the high-FPR behaviour of smaller configurations (Section~\ref{sec:eval-r1}) and the triage overhead it imposes on developers.

\section{Case 3: False Negative}
\label{sec:case-fn}
Prototype pollution missed by \texttt{CodeLlama} (LLM-only).
\begin{lstlisting}[caption={Prototype pollution (CWE-1321) returning empty findings}]
function mergeConfig(target, source) {
  for (let key in source) target[key] = source[key];
  return target;
}
mergeConfig(globalConfig, JSON.parse(req.body.config));
// Model output: []
\end{lstlisting}
Attacker-controlled \texttt{\_\_proto\_\_} keys are not flagged. A robust output would suggest guarded assignment (\texttt{Object.prototype.hasOwnProperty.call(source, key)}); demonstrates the recall limits of weaker model families.

\section{Case 4: Detection with Partial Repair}
\label{sec:case-repair-partial}
Path traversal detected; repair is only partial.
\begin{lstlisting}[caption={Path traversal (CWE-22) with under-specified repair}]
app.get('/download', (req, res) => {
  const filepath = path.join(__dirname, 'uploads', req.query.file);
  res.download(filepath);
});
// Model output: {"cwe":"CWE-22","fixedCode":"const filename = path.basename(req.query.file);"}
\end{lstlisting}
\texttt{path.basename()} reduces traversal but not authorisation; allowlist checks remain. Shows why repairs are advisory and require project-specific review (Section~\ref{sec:eval-r3}).

\section{Case 5: Multi-CWE Detection}
\label{sec:case-multi-cwe}
Hard-coded admin token plus command injection in one endpoint, both detected by \texttt{qwen3:8b+RAG}.
\begin{lstlisting}[caption={Two findings from one handler (CWE-798 + CWE-78)}]
app.post('/admin/exec', (req, res) => {
  if (req.headers['x-auth-token'] === 'admin123') { // CWE-798
    exec(req.body.command, (err, out) => res.send(out)); // CWE-78
  } else res.status(401).send('Unauthorized');
});
// Model output: [{"cwe":"CWE-798","lineStart":3},{"cwe":"CWE-78","lineStart":4}]
\end{lstlisting}
Both issues are correctly separated, which matters for IDE diagnostics and prioritisation. The credential fix is straightforward; command-execution remediation is design-sensitive.

\medskip

The five cases align with the quantitative results in Chapter~\ref{chap:evaluation}: strong model-dependent variation, persistent false-positive pressure in some modes, and a consistent need for developer oversight on repairs.
