This chapter translates the five requirements from Chapter~\ref{chap:analysis} into the conceptual design of Code Guardian --- a privacy-preserving, IDE-integrated system for detecting and repairing security vulnerabilities in JavaScript and TypeScript code using locally deployed LLMs with optional retrieval augmentation.

The design is motivated by three shortcomings in existing work: traditional SAST tools rely on predefined rules and struggle with contextual reasoning \cite{chess2004staticanalysis,bessey2010billion}; cloud-based LLM assistants require transmitting source code to external servers \cite{gdpr2016,niu2023codexleaks}; and current approaches provide limited repair guidance \cite{johnson2013don,christakis2016developers}. Code Guardian addresses these limitations through a modular architecture that directly supports the five requirements: multi-pass consensus filtering for detection accuracy (R1), JSON-mode decoding and deterministic inference for consistency (R2), a two-stage detection-then-repair pipeline for actionable remediation (R3), debouncing and caching for IDE-responsive latency (R4), and local-only inference to preserve source-code privacy (R5).

Section~\ref{sec:concept-derivation} derives the architectural decisions from the analysis results. Section~\ref{sec:system-components} describes the core components. Section~\ref{sec:detection-strategies} presents the detection workflows. Section~\ref{sec:system-architecture} provides C4 architecture views and sequence diagrams. Implementation and evaluation are deferred to Chapters~\ref{chap:implementation} and~\ref{chap:evaluation}.

\section{Summary}

This chapter translated the five requirements from Chapter~\ref{chap:analysis} into the conceptual design of Code Guardian. Starting from the gaps identified in existing tools, it derived key architectural decisions: multi-pass consensus filtering to improve detection accuracy (R1), JSON-mode decoding and deterministic inference for consistency (R2), a two-stage detection-then-repair pipeline for actionable remediation (R3), debouncing and caching for IDE-responsive latency (R4), and local-only inference via Ollama to preserve source-code privacy (R5). The chapter then described the core components, detection strategies, and optional retrieval augmentation using a local HNSW-based vector index. Finally, C4 architecture views and sequence diagrams made the privacy boundary and data flows explicit: all source code stays on the developer's machine. The next chapter explains how this concept was implemented.
