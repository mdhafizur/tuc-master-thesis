RAG improves \texttt{qwen3:8b} by +5.44 F1 points and \texttt{qwen3:4b} by +3.77 points. However, \texttt{gemma3:4b} drops by $-2.99$ points and \texttt{codellama} by $-3.26$ points with RAG enabled. This confirms that retrieval augmentation is not universally beneficial and should be treated as a model-specific configuration.

\paragraph{Statistical power.} The observed F1 differences are descriptive measurements from a single evaluation run. Exploratory exact McNemar tests on matched sample-level detection outcomes (LLM-only vs.\ LLM+RAG for each model) did not reach statistical significance for the \texttt{qwen3} improvements in this dataset ($n = 71$ vulnerable samples). This is consistent with the modest sample size: a 5-point F1 difference requires a substantially larger evaluation set to detect reliably. The RAG effect should therefore be interpreted as an indicative trend rather than a confirmed improvement, and the direction of the effect (positive for \texttt{qwen3}, negative for \texttt{gemma3} and \texttt{codellama}) is more robust than the precise magnitude.

The per-category breakdown reveals a sharp split rather than a smooth gradient. Categories with well-known syntactic signatures --- injection sinks (SQL, XSS, command injection), path traversal, and prototype pollution --- are detected at 90--100\% recall. In contrast, input validation, authentication, cryptographic misuse, and deserialization achieve 0\% \emph{type-matched} recall. However, as the qualitative error analysis in Section~\ref{sec:eval-error-analysis} shows, much of this gap is a scoring artifact: the model detects most of these vulnerabilities but labels them with more specific names than the evaluation taxonomy expects. Per-category sample sizes range from 3 to 10, so individual percentages should be interpreted cautiously; categories with fewer than 3 samples are excluded from this figure.

\subsection{Qualitative Error Analysis on Zero-Recall Categories}
\label{sec:eval-error-analysis}

The four categories with 0\% type-matched recall account for 19 of the 71 vulnerable test cases. To understand whether these zeros reflect genuine detection failures or scoring artifacts, every model response for these 19 cases was inspected manually under the best configuration (\texttt{qwen3:8b+RAG}). Three distinct failure modes emerged, summarized in Table~\ref{tab:failure-modes}.

\begin{table}[H]
\centering
\caption{Failure-mode classification for zero-recall categories (\texttt{qwen3:8b+RAG}).}
\label{tab:failure-modes}
\footnotesize
\begin{tabular}{@{}lcccp{4.8cm}@{}}
\toprule
\textbf{Category} & \textbf{$n$} & \textbf{Type mismatch} & \textbf{True miss} & \textbf{Model labels used} \\
\midrule
Insecure Deserialization & 3 & 3 & 0 & Code Injection \\
Improper Authentication  & 3 & 3 & 0 & Authentication Bypass, Timing Attack \\
Weak Cryptography        & 4 & 2 & 0 & Weak Random Number Generation, Weak Hashing Algorithm, Weak Cipher Algorithm \\
Input Validation         & 9 & 3 & 6 & Role Escalation, ReDoS, Command Injection \\
\midrule
\textbf{Total}           & \textbf{19} & \textbf{11} & \textbf{6} & \\
\bottomrule
\end{tabular}
\end{table}

\paragraph{Failure mode 1: True miss (empty output).}
Six of the 19 cases produced no model output at all. All six belong to the Input Validation category, and all six are real-world library code extracted from lodash, mongoose, moment, and serialize-javascript. These snippets contain subtle validation gaps embedded in dense utility logic or minified source. For example, a lodash internal that resolves \texttt{toStringTag} without bounds checking, or a moment.js ISO parser that accepts untrimmed date strings. The model appears unable to reason about validation requirements in the absence of an obvious sink, which is consistent with the broader pattern that local models perform best when a recognizable dangerous API call is present.

\paragraph{Failure mode 2: Correct detection, wrong type label.}
Eight cases produced findings that correctly identify the security issue but use a more specific or mechanistic label than the expected CWE-aligned category. All three Insecure Deserialization samples involve \texttt{eval()}-based deserialization; the model labels them ``Code Injection'' --- technically accurate, since \texttt{eval()} is the injection vector, but the harness expects the higher-level CWE-502 label. Similarly, the three Improper Authentication samples are labeled ``Authentication Bypass'' or ``Timing Attack'' rather than the umbrella ``Improper Authentication''. In both cases the suggested fixes are appropriate (replace \texttt{eval()} with \texttt{JSON.parse()}; use constant-time comparison), confirming that the underlying detection is sound.

\paragraph{Failure mode 3: Hierarchical label inconsistency.}
Two of the four Weak Cryptography cases exhibit a subtler variant of label mismatch. The model detects all cryptographic weaknesses (MD5, DES, \texttt{Math.random()}) in every case, but its labeling is inconsistent: for two cases it uses the exact expected label ``Weak Cryptography'', while for two structurally identical cases it uses sub-type labels (``Weak Hashing Algorithm'', ``Weak Cipher Algorithm'', ``Weak Random Number Generation''). The difference appears to depend on prompt phrasing rather than code content, since the underlying code patterns are similar across all four cases.

\paragraph{Construct validity implications.}
Of the 19 zero-recall cases, 11 (58\%) are scoring artifacts caused by type-label vocabulary mismatch rather than detection failures. If these 11 cases were re-scored at the sample level (``did the model flag any relevant issue?''), the effective sample-level detection rate for the four categories would rise from 0/19 to 11/19 (58\%), and overall recall would increase by approximately 5 percentage points. This finding highlights a known limitation of type-level matching in LLM-based detection: models generate natural-language labels that may be semantically correct but lexically different from the evaluation taxonomy~\cite{li2025correct}. The true detection gap --- cases where the model produces no output at all --- is concentrated in real-world library code with implicit validation requirements, a genuinely harder task that warrants targeted evaluation in future work.

\subsection{SAST Baseline Comparison}

SAST tools show a different trade-off profile. Semgrep achieves low FPR (6.67\%) but very low recall (9.73\%). CodeQL has higher FPR (53.33\%) with similarly low recall. ESLint security plugins detect none of the test cases. The LLM-based approach trades higher FPR for substantially better recall, making it more suitable for comprehensive security audits while SAST remains useful as a low-noise complement.

\paragraph{FPR confidence intervals.} Because the secure-sample set contains only $n=30$ cases, FPR point estimates carry wide uncertainty. For the best configuration (\texttt{qwen3:8b+RAG}, 6 of 30 flagged, FPR = 20\%), the 95\% exact binomial confidence interval is $[7.7\%, 38.6\%]$. For configurations that flag all 30 secure samples (FPR = 100\%), the 95\% CI lower bound is 88.4\%. These intervals should be kept in mind when interpreting FPR differences across configurations.
