\subsection{RAG Ablation Impact on Accuracy}

RAG effects are strongly model-dependent (see the LLM-only / LLM+RAG rows in Table~\ref{tab:eval-r1-all}).

RAG lifts \texttt{qwen3:8b} F1 from 67.52\% to 71.94\% ($+4.42$ points) and pushes its precision from 61.63\% to 73.53\% while halving FPR (50.00\% $\to$ 10.00\%). RAG is roughly neutral on \texttt{gemma3:1b} and \texttt{gemma3:4b}, slightly hurts \texttt{qwen3:4b} ($-5.22$ points), and dramatically degrades \texttt{codellama} ($-29.89$ points: F1 drops from 53.06\% to 23.17\%, latency nearly doubles). The \texttt{codellama+RAG} collapse is the strongest negative-RAG observation in the dataset and indicates that the additional retrieval context actively confuses \texttt{codellama}'s output structure rather than grounding it. Retrieval augmentation is therefore a model-specific configuration, not a universal default. Exploratory exact McNemar tests on matched sample-level outcomes for the \texttt{qwen3} improvements did not reach significance ($n=71$); the RAG effect is best read as an indicative trend whose direction (positive for \texttt{qwen3}, negative for \texttt{codellama}) is more robust than the precise magnitude.

\subsection{Per-Category Detection Breakdown}

Per-canonical-category recall on \texttt{qwen3:8b+RAG} (3-runs pooled, categories with $\geq 3$ samples) shows a sharp split rather than a smooth gradient. Categories with well-known syntactic signatures --- SQL injection (90\%), XSS (100\%), command injection (100\%), path traversal (100\%), prototype pollution (100\%), weak-crypto, hardcoded credentials, LDAP injection, and SSRF (each 100\%) --- are detected at 90--100\% recall when the dangerous API is lexically obvious. In contrast, improper-auth, input-validation, and weak-encryption score 0\% recall, and deserialization only 33\%. Section~\ref{sec:eval-error-analysis} shows a substantial share of this gap is a labelling artefact rather than detection failure: the auth-bypass canonical category, for instance, absorbs nine model findings on cases the dataset labels \emph{improper-auth}, which simultaneously show up as nine false positives on auth-bypass and nine misses on improper-auth.

\subsection{Qualitative Error Analysis on Zero-Recall Categories}

(Two other categories that scored 0\% under the previous substring matcher --- weak cryptography and insecure deserialization --- recovered to 100\% and 33\% respectively when the canonical matcher absorbed sub-type labels such as ``Weak Hashing Algorithm'' and ``Weak Random Number Generation''.)

The two residual gaps differ in kind. Every \emph{improper-auth} case is detected and emitted as \emph{authentication-bypass} or \emph{timing-attack} --- canonical siblings of \emph{auth-bypass} --- so the underlying detection and the suggested fixes (constant-time comparison, JWT algorithm validation) are correct and merging the buckets would lift recall from 0\% to 100\% at the cost of conflating two CWE-aligned classes. The 9 input-validation samples (27 evaluations) are extracted from real-world libraries (lodash, mongoose, moment, serialize-javascript) where the validation gap is implicit in dense utility logic; the model produces no output for them. This is the residual recall gap the canonical taxonomy cannot recover --- it requires cross-file or taint-flow context, not a labelling refinement.

\subsection{SAST Baseline Comparison}

SAST tools show a different trade-off profile. Semgrep achieves the lowest FPR (6.67\%) but a low recall (12.68\% under canonical matching); CodeQL has higher FPR (53.33\%) with similar low recall (9.86\%); ESLint security plugins detect none of the test cases. The LLM-based approach trades higher FPR for substantially better recall, making it more suitable for comprehensive security audits while SAST remains useful as a low-noise complement. The hybrid SAST-fusion option (Section~\ref{sec:eval-refined-config}) operationalises this complementarity by promoting LLM findings corroborated by Semgrep to confidence~$1.0$. FPR is computed at sample level over $n=30$ secure cases; the 95\% exact binomial CI for the headline 10\% FPR is $[2.1\%, 26.5\%]$, and for 100\%-FPR configurations the lower bound is 88.4\%.

The canonical effect is positive on every model and mode, with deltas ranging from $+0.64$ to $+10.17$ F1 points (mean $\approx +5.5$). Because the lift comes entirely from re-binning labels --- no new model calls --- it is a deterministic methodology adjustment rather than a model-quality claim.

\subsection{External-Corpus Stress Test}
\label{sec:eval-r1-external-corpus}

To probe the substitution disclosed in Section~\ref{sec:eval-benchmark-substitution} the analyser was rerun on the 15-case external corpus (11 vulnerable + 4 secure) drawn from OWASP NodeGoat, OWASP Juice Shop, and three named CVEs (CVE-2022-24999, CVE-2021-23337, CVE-2022-24771). The configuration is intentionally conservative: \texttt{qwen3:8b}, LLM-only (no RAG), single run per sample (no inter-run consensus), no confidence gate. This is a stress test, not a parity comparison with the headline.

Two effects compound in the gap. First, the external corpus skews toward weakness classes that require cross-file or framework-level reasoning: mass assignment, broken access control on an admin route, JWT \texttt{none}-algorithm acceptance, signature verification (CWE-347), and Lodash \texttt{\_.template} code injection. Five of the six false negatives are in this class. The detector's single-function scope (Section~\ref{sec:impl-pipeline}) does not see the access-control wrapper, the JWT \texttt{algorithms} option, or the version constraint that resolves the CVE. The thesis's existing input-validation gap (Section~\ref{sec:eval-error-analysis}) is the same limitation surfacing on a corpus designed to elicit it. Second, the configuration is two notches weaker than the headline: no retrieval and a single inference per sample remove the precision gains attributed to canonical matching plus the inter-run confidence gate at $\geq 0.67$ (Section~\ref{sec:eval-r1-confidence}).

The result is therefore best read as a quantification of the substitution penalty under deliberately weak conditions, not as a measurement of the system's whole-project capability. The latency rise (median 9\,462\,ms vs.\ 1\,573\,ms) reflects longer per-snippet code (full route handlers vs.\ single functions); inference time scales with prefill length, consistent with the latency-component analysis in Section~\ref{sec:eval-r4}. Closing the gap with the headline configuration --- LLM+RAG, 3 runs, confidence gate --- is named as future work alongside cross-file context modelling.

\paragraph{Diagnosis of the 0\,\% recall.}
The detector did not stay silent --- it produced 14 plausible findings on real NodeGoat code, including reflected XSS in \texttt{routes/contributions.js}, dynamic-template path injection in \texttt{routes/tutorial.js} (CWE-94/95-class), three session-fixation observations in \texttt{routes/session.js}, deprecated \texttt{bcrypt-nodejs} usage in \texttt{data/user-dao.js}, error-stack exposure in \texttt{routes/error.js}, and an open-redirect-shaped pattern in \texttt{routes/index.js}. None of these match the curated documented list. The 0\,\% recall decomposes into four mechanisms, all of which the existing limitations section anticipated:

\begin{itemize}
  \item \emph{Out-of-scope file types.} 2 of 10 documented entries point at non-JS/TS files: the reflected-XSS path in \texttt{app/views/contributions.html} (HTML, not scanned) and the vulnerable-dependency entry in \texttt{package.json} (JSON, not scanned). The function-scoped analyser is by design a code-only scanner.
  \item \emph{Cross-file flows.} The CSRF, weak-session, and mass-assignment entries depend on session middleware in \texttt{server.js} interacting with route handlers in \texttt{routes/profile.js}; the function-level scope cannot see both halves at once. This is the same input-validation gap measured in Section~\ref{sec:eval-error-analysis}.
  \item \emph{Canonical-taxonomy under-coverage.} 10 of 14 findings normalise to the \texttt{other} bucket because the canonical taxonomy is JS-injection-centric (Section~\ref{sec:eval-r1-canonical}); session-fixation, deprecated-dependency, and weak-password-regex weaknesses have no taxonomy bin, so they cannot match a documented entry even when the underlying weakness is the same OWASP class.
  \item \emph{True misses.} The SQL injection in \texttt{data/allocations-dao.js} and the MD5 hashing in \texttt{data/profile-dao.js} are within scope, were chunked correctly, and were missed by the model. These are genuine LLM-side false negatives on real-project code under the LLM-only single-run configuration.
\end{itemize}

\paragraph{Reading.}
The whole-project run validates the thesis's existing function-scope limitation rather than refuting the headline numbers: the detector finds plausible real weaknesses on real code, but its recall against a human-curated vulnerability list is bounded by what a function-level scope can see. Closing the gap requires expanding the canonical taxonomy (a deterministic change with no Ollama cost), promoting the configuration to LLM+RAG with consensus and confidence gating (a parity rerun), and most importantly modelling cross-file context so that middleware-route flows become visible. All three are named as future work.

\subsection{Level Mapping}

Based on the R1 evaluation scale (Table~\ref{tab:r1-accuracy-thresholds}), the best configuration (\texttt{qwen3:8b+RAG}) maps as follows under canonical matching:

\begin{itemize}
  \item F1 = 71.94\% $\rightarrow$ falls in $[0.60, 0.75)$
  \item Precision = 73.53\% $\rightarrow$ above 0.70
  \item Recall = 70.42\% $\rightarrow$ above 0.70
  \item FPR = 10.00\% $\rightarrow$ comfortably below the $\leq 0.20$ boundary
\end{itemize}

Three of the four metrics meet the High threshold (precision, recall, FPR) but F1 is in the Medium band (just below 0.75). Applying the inter-run confidence gate at $\geq 0.67$ lifts F1 to 73.13\% and precision to 77.78\% (Section~\ref{sec:eval-r1-confidence}), which still falls in the Medium F1 band but tightens precision further.
